# Phase 2.5 plan and acceptance criteria

Baseline: clean `main` at `76403a5acaf8a9e1426da0fe581a1f3d005593d2`. Phase 2 app/database are healthy. PostgreSQL and attachments use separate named volumes; PostgreSQL has no published port. The normal database has 15 rooms and no users/tenants. BackupHistory currently has status/checksum/storage metadata but no executor, size or error fields. No HTTPS proxy or backup implementation exists. Local environment values are ignored and will not be published.

1. Add a small maintenance image with PostgreSQL 17 client tools, Node and rclone. Back up a PostgreSQL exported snapshot plus immutable copies of attachments and a versioned manifest. Compare attachment hashes across the snapshot window; fail rather than certify an inconsistent set.
2. Encrypt complete sets using AES-256-GCM with a private 32-byte key file. Verify authenticated decryption, manifest hashes and isolated PostgreSQL/attachment restoration before marking a set successful. Preserve unsuccessful attempts as failures, never as verified backups.
3. Use a kernel file lock to prevent overlapping jobs. Run a persistent scheduler every minute, with Sunday 02:00 Asia/Bangkok weekly eligibility and catch-up after downtime. Retain twelve verified weekly sets, retaining pending uploads until copied. Keep a separate bounded manual history. Retry cloud uploads hourly and after each backup, verify the remote encrypted bytes, and use atomic remote filenames. Never delete the last verified set because a later job fails.
4. Extend BackupHistory additively with archive size, error, verification and upload timestamps. Keep a private on-disk status journal so failures remain visible if PostgreSQL is unavailable. Archive names contain only timestamps/UUIDs, never tenant information.
5. Provide host commands for initialization, manual backup, status, upload retry, isolated restore drills and owner-confirmed production recovery. Restore drills create separate Docker volumes/networks and reject production database targets. Production recovery requires a typed confirmation, a verified rollback backup and application downtime; it is not executed during development.
6. Add Caddy internal-CA TLS using a Compose overlay that removes the app's published HTTP port, sets Secure cookies and an exact HTTPS origin, and exposes only HTTPS on a configured private interface. Persist the CA; export only its public root certificate. Verify TLS with that root, never by disabling validation.
7. Execute backup/encryption/corruption/retention/retry/locking/scheduling tests, an isolated end-to-end restore with real records and attachments, HTTPS login/CSRF/cookie/network tests, restart persistence and Phase 1/2 regressions. Record initial failures and their fixes.
8. Write operations guides and final report. Inspect upstream head and staged files, commit as a descendant of current `main`, push without force and read back the commit. Stop before Phase 3.

Acceptance requires a real encrypted local set restored into an isolated database, matching schema/room/tenant/lease fingerprints and attachment hashes, with a restore receipt tied to its encrypted checksum. Cloud delivery remains Partial until the owner authorizes rclone and a verified upload runs. Physical-device certificate trust remains NOT RUN until the owner commissions those devices. Phase 3 readiness is conditional on those remaining operational steps, not inferred from passing code tests.

# Phase 4 expense implementation contract

Status: architecture proposal for independent review. No expense implementation or financial approval is claimed by this document.

## Grounding and scope

The installed Pstack Codex adapter and architect, TypeScript, domain modeling and unslop guidance were read for this assignment. The parent requested one bounded design agent and no further spawning. Two alternatives below were evaluated locally; the separate independent review must challenge the selected contract before implementation. This is not a claim of a multi-model arena run.

The actual foundation schema has `ExpenseCategory(id, name, kind, createdAt, updatedAt)` and `Expense(id, propertyId, categoryId, description, amount, occurredAt, isDemo, createdAt, updatedAt)`. Category names are globally unique. `Expense.amount` is NUMERIC(14,2) with an existing positive CHECK. Property/category FKs use RESTRICT. Existing attachments may refer to an expense, but upload and private evidence lifecycle are separate unfinished work.

`docs/implementation-plan.md` Phase 4 requires persisted audited OPEX/CAPEX categories and approvals. `docs/phase-2-architecture.md` assigns classification to ExpenseCategory. `docs/system-architecture.md` requires reversal/void semantics for financial records. `src/features/expenses/screen.tsx` is still a demo-memory workflow. It collects title, vendor, category, kind, amount, date, cash/transfer and note. Its aggregate selectors and CSV are demo behavior, not proof of a persisted ledger. No documented approval amount thresholds, tax, depreciation, reimbursement, accounts-payable or bank reconciliation rules were found.

This unit persists expense entry, approval/posting, cancellation/reversal, category creation/deactivation, filtered reads and exact totals. It does not implement asset depreciation or claim statutory accounting or tax compliance. The authoritative category supplies OPEX/CAPEX; the expense form cannot submit a conflicting kind.

## Alternatives and selected shape

Candidate A posts each ADMIN-created expense immediately, with an immutable amount and a later reversal. It uses fewer states but cannot represent the approved Phase 4 requirement for an approval workflow or STAFF preparation without extra exceptional paths.

Candidate B stores immutable pending entries, then permits ADMIN posting, pending cancellation and full reversal. It adds one command table and lifecycle metadata to the existing Expense table. Every financial change has one explicit transition. Candidate B is selected because it represents approvals without inventing a second payment ledger. A correction is cancel/reverse then a new expense, linked by an optional correctionOfId. It never edits a posted original.

The following are proposed conservative development defaults under the Owner's broad delegation, not historical policies or separately accepted Owner decisions: STAFF and ADMIN may prepare entries; ADMIN posts, cancels and reverses; all amounts require ADMIN approval; cash and bank transfer are supported; full reversal only; vendor is required for new managed entries; new categories are ADMIN-maintained; category name/kind remain immutable; posting records an operator assertion that the expense was paid. The reviewer and orchestrator must record adoption or revision explicitly before implementation. No new request for blanket permission is implied.

## Lifecycle and schema

Use `ExpenseStatus = PENDING | POSTED | CANCELLED | REVERSED` for managed rows. Add nullable status and nullable managed-only metadata to existing Expense. Add `legacyUnmapped Boolean @default(true)` so old rows keep original values and are never silently approved. New service inserts explicitly set legacyUnmapped=false, isDemo=false and PENDING. Existing rows retain null lifecycle metadata and remain outside managed totals, with a visible excluded legacy count. A migration must not assign POSTED, actors or inferred vendor/method to old records. Backfill the legacy discriminator only for rows already present during migration. After that backfill, a BEFORE INSERT trigger must reject every new Expense row unless legacyUnmapped=false with the complete managed PENDING shape and current authorized actor. Omitted/default-true legacyUnmapped must fail, including direct SQL. No runtime opening-import bypass or new legacy insertion is provided. Test omitted discriminator, explicit true, null status and forged legacy-shaped direct INSERT failures.

Managed fields include version starting at 1, vendor VarChar(120), method CASH or BANK_TRANSFER, note VarChar(500) nullable, recordedById, postedById/postedAt, cancelledById/cancelledAt/cancelReason, reversedById/reversedAt/reverseReason, categoryNameSnapshot and categoryKindSnapshot. Capture category snapshots at creation and keep the category's name/kind immutable. Use existing description VarChar(200) for title, amount Decimal(14,2), occurredAt DATE, property and category IDs. Add correctionOfId nullable self-FK with RESTRICT; a correction may refer only to an earlier managed CANCELLED or REVERSED expense on the same property. No sum matching or automatic refund is inferred.

PENDING may become POSTED or CANCELLED. POSTED may become REVERSED. CANCELLED and REVERSED are terminal. Posting and reversal each advance version by exactly one. Cancellation also advances version by one. No DELETE or financial/content edit is permitted for managed rows, including pending rows. To fix an input mistake, cancel and prepare again. All transition actors/timestamps/reasons must have the exact required null/non-null shape. A reversed row retains its original posted actor and timestamp. Legacy fields cannot be changed through these commands. Do not expose a generic ORM update endpoint.

Add `ExpenseCategory.active Boolean @default(true)` and category version starting at 1. Retain category name's existing global uniqueness and existing kind values. ADMIN can create or change active state; no rename, reclassification or deletion in this unit. An inactive category remains readable for history. Creating and posting an expense requires an active category, with a row lock shared with deactivation. A pending expense whose category was deactivated can be cancelled and replaced. Categories are a shared catalog as the existing schema defines, not silently converted to per-property uniqueness. Trim names and reject control characters; preserve the existing database case-sensitive uniqueness semantics instead of inventing Unicode/case equivalence.

Add `ExpenseCommand(id, actorId, commandKey, operation, requestFingerprint, result, createdAt)` with unique(actorId,commandKey), restrictive actor FK and immutable records. Expense and category commands share this namespace. No new sequential expense number is needed; display the UUID or a short UI identifier without claiming receipt numbering. This adds one table. Update restore inventory using a new frozen version registry after integrating any deposit tables; never expand historical v2/v3 registries in place. The schema owner must reconcile concurrent migrations and User relation names before coding.

## Database constraints and transaction boundaries

The migration must enforce managed/legacy null shapes, allowed transitions, exact one-step version changes, immutable financial/content/classification/origin fields and immutable command rows. Protect DELETE for original expense rows with financial history and their categories. Enforce category snapshot equality on creation using the category row, rather than trusting a correctly hashed arbitrary snapshot. Category name/kind are immutable at database level. New managed rows require an existing enabled actor and correct role for the action. Application role checks remain mandatory; triggers are integrity protection and do not replace HTTP authentication.

Use PostgreSQL triggers and CHECKs together, consistent with the reviewed payment migration. A CHECK cannot validate a joined category or previous lifecycle state. No trigger may silently repair input. Do not change or drop existing constraints/indexes/FKs. Verify direct SQL cannot bypass the managed rules. Ordinary application DB credentials are not assumed to defeat a database superuser.

For every mutation, begin one transaction, acquire the existing shared source gate, re-read and authorize the current enabled actor, take the actor/command advisory lock, resolve a prior matching command, then lock category before expense. The same category lock serializes category deactivation and posting. Re-read state and expectedVersion after locks. Resolve property existence inside the transaction. Property has no isDemo field. Reject demo expenses and any related entities that actually define isDemo; do not invent a property discriminator. Write row transition, audit log and immutable command result atomically. On any failure none commits. Use bounded retries only for observed PostgreSQL serialization/deadlock errors, following existing payment service behavior. Never rerun a committed command with a new key automatically.

Audit actions are `expense.create`, `expense.post`, `expense.cancel`, `expense.reverse`, `expense.category.create` and `expense.category.set-active`. Record entity ID, actor, command key, canonical request fingerprint and exact before/after financial state. Include reasons and correction linkage. Do not log credentials or attachment contents. A rollback caused by audit or command insertion failure must leave no partial approval.

An identical actor/key and canonical request returns the stored response after current actor authorization. Reusing the key for a different operation/payload fails 409. UUID inputs normalize case before fingerprinting. Normalize optional blank text once at the input boundary. No Number or float conversion enters amounts, sums, fingerprints or CSV. Bank method does not prove settlement. This module has no bank outgoing-reference uniqueness rule because no approved reference/account identifier exists.

Duplicate submissions are prevented by command idempotency. Independently submitted expenses with identical vendor/date/amount can be legitimate; do not reject them or silently merge. Show a non-blocking possible-duplicate warning for the same property, trimmed vendor, occurredAt and amount among PENDING/POSTED rows. Describe it as a warning, not verified duplicate detection. Do not infer a new mandatory override policy.

Amount is an explicit positive decimal string matching NUMERIC(14,2), up to `999999999999.99`. Require a real Gregorian ISO calendar date, never a timezone-converted browser midnight. Method is a strict CASH/BANK_TRANSFER union. Enforce bounded strings, canonical UUIDs, strict unknown-key rejection, pagination max 100 and bounded search. Reject invalid property/category and demo entities. No future-date or accounting-period lock policy is invented here; occurredAt is the operator-entered expense date and the UI must explain this. Inputs with more than two decimal places fail rather than round.

DTOs return fixed two-decimal strings, ISO dates, lifecycle/version, frozen category name/kind, vendor/method/note, actor/timestamp/reason metadata and correction linkage. List filters include property, from/to inclusive DATE bounds, kind, category, status, offset/limit and description/vendor search. Order by occurredAt descending, createdAt descending, id descending. List and summary use the same predicates and one consistent database snapshot. Return scope `managed-only` and excluded legacy count separately. Never combine demo and managed totals.

Routes are GET/POST `/api/v1/expenses`, GET `/api/v1/expenses/[id]`, POST `/api/v1/expenses/[id]/{post,cancel,reverse}`, GET/POST `/api/v1/expense-categories`, and POST `/api/v1/expense-categories/[id]/active`. Preserve the existing trailing slash convention. Use requireActor, checkOrigin on mutations, bounded readJson, strict schemas, no-store envelopes and generic handle error behavior. Reads are authenticated STAFF/ADMIN; financial approval/category mutations require current ADMIN. Disable unsupported controls but test server denials independently.

Avoid writing to `src/features/live/workspace.tsx`, invoice services or receipt PDF code. The implementation owner owns expense files/schema migration/tests; a separate reviewer owns evidence findings. Main orchestrator integrates shared schema/User relation changes and restore-registry dependencies. A later reporting owner consumes the expense query contract, not expense UI state.

## Reporting semantics and explicit limits

For this unit, approved expense totals group POSTED managed rows by occurredAt and frozen category kind. PENDING/CANCELLED/REVERSED rows contribute zero. OPEX and CAPEX are reported separately; their sum is total recorded expenses. Reversal is a correction of recorded history, not proof that cash was refunded. Reversing October's expense in November therefore changes October's current ledger total; it does not fabricate a November cash inflow. UI and exports must label these as recorded approved expenses and expose reversed history.

Do not label these figures statutory profit, depreciation-adjusted earnings, reconciled bank cash flow or immutable period-close reports. A later report that computes received payments minus approved expenses must label its exact dates and correction semantics. Deposits remain outside rental revenue and expense totals. No automatic expense, deduction or revenue is created from a deposit operation. Tax/VAT/withholding, accrual invoices, fixed assets, depreciation, reimbursement and physical refunds require a later explicit business contract.

CSV export uses the same filters/authorization and exact decimal strings. Escape cells and neutralize spreadsheet formula injection for untrusted text; do not mutate stored text. Export status and reversal metadata so a user can distinguish history. Fetch all matching rows through a bounded server export or explicit paging, never silently export only the first displayed page.

1. Unit tests call strict boundary schemas and actual domain totals. Cover max amount, satang, overflow/negative/exponent/extra decimal rejection, invalid calendar dates, unknown fields, UUID aliases, lifecycle denial and exact OPEX/CAPEX results. Formatting tests must not substitute for ledger checks.
2. Disposable PostgreSQL tests run the real migration on the previously approved schema, preserve existing Expense/Category/Attachment bytes and original constraints, and demonstrate null legacy metadata with no invented approval. Fresh migrated schema and real Prisma generation must pass.
3. PostgreSQL service tests cover STAFF preparation and ADMIN approval, role change/disabled user, nonexistent property/category IDs and global-category eligibility, inactive category, idempotent replay/conflict, foreign actor key isolation, stale versions, cancellation, reversal, immutable originals and same-property correction linkage. Audit/command failure injection proves complete rollback.
4. Independent simultaneous transactions race post/post, post/cancel, reverse/reverse and post/category-deactivate. For post/post, post/cancel and reverse/reverse, exactly one conflicting transition commits. For post/category-deactivate, assert valid serialized outcomes: if posting locks the active category first, posting and subsequent deactivation may both commit; if deactivation locks first, it commits and posting rejects the inactive category. A posted expense remains valid historical data after later category deactivation. Never require exactly one commit for that non-conflicting serialized order. Direct SQL tests attempt forged category snapshots, changed money/vendor/kind/origin flags, invalid actors, skipped lifecycle states, changed commands and DELETE. Verify invariants from the database after failures.
5. Integration fixtures create OPEX 1234.56 and CAPEX 10000.01, pending 5.00, cancelled 7.00 and reversed 9.99. Filtered POSTED totals must be exactly 1234.56, 10000.01 and 11234.57. Prove date-boundary inclusion, category snapshots, paging, excluded legacy rows, reversal corrections and no deposit double count.
6. Agent browser UAT uses synthetic property/category/users. Development complete, integrated, agent UAT complete and deployed are separate statuses. No production approval or test result is established by this proposal.

## Reconciliation with deposit review and remaining decisions

The Stage 3E review DRE-01 rejects undeclared reversal chains. This expense shape follows that constraint: REVERSED is terminal, its reversal metadata cannot be reversed again, and corrections create a new explicit expense. DRE-02's rent/deposit receiving-reference collision does not apply to outgoing expenses; do not reuse incoming transfer identities to impose outgoing uniqueness. DRE-03 requires totals to reconcile reversals; the expense DTO therefore returns original lifecycle history plus explicit POSTED-only totals over the entire filtered result, not only its page. Both modules must share this meaning before consolidated reports ship.

The deposit proposal's D3E-03 and D3E-09 require retained evidence for deductions. An expense's optional Attachment relation is not that evidence mechanism and does not authorize deposit deductions. No deposit or expense implementation may manufacture a receipt, refund or expense from the other's ledger. If later requirements mandate attachments for particular expense kinds, that is a distinct upload/evidence contract and acceptance gate.

The concrete choices still needing orchestrator adoption and independent review are the pending/ADMIN workflow, immutable pending entries with cancel/recreate correction, globally shared immutable category classification, and restating historical approved expense totals when a later reversal corrects an earlier record. The Owner's broad delegation permits routine engineering decisions; these items do not inherently require another Owner prompt. They must be recorded as selected policies rather than represented as facts already stated in an old specification. No financial tax rule needs to be guessed to implement this bounded unit.

Before a production consolidated finance report, the expense and deposit designs must agree whether report periods are revisable or whether closed periods require dated correcting entries. This proposal explicitly chooses revisable current expense views and does not implement accounting period close. If the reviewer requires immutable closed statements instead, change the date/reversal data model before code rather than silently changing totals later.

Remaining implementation integration decisions are the exact new migration timestamp, Prisma relation names shared with receipt/deposit work, and the next inventory version after the integrated schema is frozen. These are coordinator-owned engineering choices. Legal/tax treatment, depreciation, mandatory receipt documentation and real historical mapping remain outside this unit and unverified.

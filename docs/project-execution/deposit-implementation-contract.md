# Stage 3E managed deposit implementation contract

Status: concrete design for Main Agent review and adoption. No schema, posting service, upload API or financial test result is established by this document. It supersedes the unresolved choices in `deposit-domain-design.md` for this bounded implementation after adoption. Original design and review remain the decision history.

## Grounding and design choice

The actual `Lease.deposit` is a contractual NUMERIC(14,2) requirement. `SecurityDeposit` has only lease, kind, amount, occurredAt, demo flag and timestamps. It has no verified actor, command identity or reversal link. Preserve its rows and original constraints byte-for-byte. The existing Payment service owns invoice allocations and rental receipts, including actor-scoped replay and case-sensitive trimmed receivingAccountKey/externalReference identity. Deposits do not enter that allocation model.

`Attachment` is metadata with exactly one tenant/lease/payment/expense owner. It is not a ready upload subsystem. Docker already mounts a private ATTACHMENT_DIR, and operations backup inventories Attachment paths/hashes/bytes and copies that volume. There is no verified upload route to reuse. A private evidence implementation below is a required engineering dependency, not a reason to pretend a metadata row proves possession of a file.

Candidate A extends SecurityDeposit with nullable managed provenance and many legacy exceptions. Candidate B adds a dedicated managed ledger and preserves the old table as an unverified stream. Choose B. This keeps managed INSERT rules and append-only history uniform and avoids inferred settlement. Approximately 15 rooms need no cached balance.

This task read the installed Pstack adapter, architect/how, TypeScript/type-system and unslop guidance, actual schema, payment identity/locking, source-gate usage and backup attachment inventory. Two alternatives were compared locally. No additional arena or cross-provider review is claimed. Main supplies the independent design review. No framework code is written here; implementation must read installed Next.js guides before routes/pages.

## Selected development policies

Main may adopt these concrete defaults under the Owner's standing completion authorization. They are selected policies, not claims that old specifications already settled them.

ADMIN alone posts receipts, refunds, deductions, reversals and historical reviews. STAFF and ADMIN read. Posting is an explicit assertion that the operator verified funds or the documented settlement; no bank API pays or verifies anything. The UI explains that assertion and requires it in the strict command. Full reversal only; never edit/delete a posting. Every money movement or deduction requires one retained private evidence file and a bounded description. A multi-page PDF can collect several supporting pages.

Receipts accept positive top-ups without changing Lease.deposit. New receipts require an ACTIVE non-demo lease and non-demo tenant. DRAFT leases reject financial posting. ENDED/CANCELLED leases may refund held liability, apply documented settlement deductions, or correct a previous posting with a reason. They may not receive a new top-up. A reversal of an earlier refund may restore liability on an ended/cancelled lease because it corrects history. No automatic rent offset, damage revenue, expense, tax or payment allocation is created.

Record actual occurrence as a required timestamp with explicit offset, normalized to UTC, and posting as database time. Reject future occurrence beyond five minutes of the server clock. Older timestamps are permitted with an explanation. Availability is validated in posting order, not by pretending every backdated effective-time prefix is nonnegative. Reports identify effective date and posting date and remain revisable current-ledger views; no closed-period statement promise exists. This matches the expense design's current-history correction semantics.

Cash receipt requires evidence and an operator assertion. Refund requires method CASH/BANK_TRANSFER, payee name snapshot, reason, evidence and settlementReviewed=true. Bank refund additionally records outgoing reference and payee destination description, distinct from incoming receiving-account identity. These are operator assertions, not proof of actual payment. Deduction requires reason/evidence but has no invented bank fields or automatic revenue classification.

## Managed data shape

Add five tables in a later controlled migration after the expense baseline. Final names/Prisma relations are coordinator-owned, but the shapes below are the agreed logical interface.

1. `DepositAccount`: leaseId primary/restrictive FK, version, reviewState UNREVIEWED/REVIEWED, reviewedById, reviewedAt, legacyDigest, reviewReason, evidenceId and original openingAmount. Review fields form one immutable transition. An account starts version 0. Every successful financial entry increments version exactly once. The account has no mutable cached balance.
2. `DepositEntry`: id, leaseId, sequence, kind RECEIPT/REFUND/DEDUCTION/REVERSAL/OPENING, amount NUMERIC(14,2)>0, occurredAt, postedAt, postedById, reason, evidenceId, method-specific provenance, reverseOfId nullable unique, documentNumber unique, documentSnapshot JSON and SHA-256. Unique(leaseId,sequence), restrictive relations and joined same-lease rules apply. Entry content and provenance are immutable. Snapshot fields derive from authoritative locked rows, not caller JSON. OPENING is reviewed starting liability and has no cash receipt classification.
3. `DepositCommand`: actorId/commandKey unique, operation, canonical request fingerprint, immutable complete result and createdAt. Shared namespace across review and financial deposit commands. Current authorization precedes replay; conflicting payload returns 409. Audit, command, account version and entry commit together.
4. `DepositEvidence`: id, leaseId, attachmentId unique/restrictive FK, uploadedById, acceptedAt. Only the verified upload operation creates it after retaining the file. Attachment retains its existing leaseId owner, not a forged extra owner. Deposit entries reference evidence on the same lease. Freeze referenced Attachment content/owner/path/hash/bytes and all evidence rows. Reuse a file for multiple entries only on the same lease, with every link visible in history; evidence does not itself prove the financial assertion.
5. `DepositDocumentCounter`: Bangkok Gregorian YYYYMM key and nextValue. Atomically assign never-reused sequential numbers, e.g. DEP-202610-000001. The series covers deposit events with visible kind; a reversal has its own document and references the original number. Counter exhaustion fails atomically and never wraps. Changing a prefix is not a legal receipt determination.

All managed money must be finite. PostgreSQL NUMERIC(14,2) admits NaN, and a positive comparison alone does not reject it. Entry amounts and positive opening values require CHECK(amount <> 'NaN'::numeric AND amount > 0 AND amount <= 999999999999.99). The account review's zero-capable opening field requires explicit NaN rejection and the inclusive 0..999999999999.99 range. The strict input parser rejects NaN, infinities and exponent forms before SQL, but database guards remain mandatory for raw writers. Derived sums and signed effects must reject non-finite operands/results without limiting aggregate precision to one entry. Add direct SQL INSERT/UPDATE and review-path attempts using 'NaN'::numeric, as well as infinities and invalid signs, and verify complete rollback. Existing legacy rows are preserved; this rule governs the new managed representation.

All managed rows reject invalid current actors, skipped account versions, forged snapshots, unsupported method-field combinations and update/delete attempts. Account identity and approved review metadata are immutable. Legacy SecurityDeposit is neither relabeled nor included in managed sums. Do not backfill DepositAccount reviews or OPENING entries from lease requirements or legacy sums.

Historical review locks the lease and original rows, computes a canonical digest over all original legacy columns ordered by id, and records the operator's verified opening liability with evidence and reason. Zero opening creates no positive-money entry but still records the review/version transition and audit. Positive opening creates one OPENING entry, document and command atomically. A lease without old deposit rows may explicitly initialize reviewed opening zero through the same operation. No spending or new receipt is allowed until review completes. If original legacy rows later differ from the recorded digest, all further financial posting fails closed pending an explicit reviewed reconciliation extension; never silently reset the opening.

The review amount is an operator-supplied verified liability, not a declaration that the old gross sum is cash. Review metadata, legacy gross figures and contractual requirement stay separately visible. A second opening or editing the original opening is forbidden. Correcting a positive OPENING uses a full reversal then an explicit supported correction receipt only if its semantics are actual new funds; historical re-opening corrections need a separately reviewed adjustment command rather than mislabeling them cash. The first implementation must show that limitation instead of inventing a fake receipt.

## DRE-01 reversal rules and DRE-03 equations

REVERSAL targets exactly one earlier original RECEIPT, REFUND, DEDUCTION or OPENING on the same lease, copies its exact amount, and has its opposite effect. It cannot target REVERSAL or an already-reversed entry. Both SQL and service enforce this. Reversal of a receipt/opening rejects if the resulting held liability is negative. No automatic reversal chain or related-payment cancellation occurs.

For the complete managed ledger, expose gross original amounts and reversal amounts by target bucket. Let R/F/D/O be gross RECEIPT/REFUND/DEDUCTION/OPENING sums. Let RR/RF/RD/RO be sums of reversal amounts targeting those original kinds. Then netReceipts=R-RR, netRefunds=F-RF, netDeductions=D-RD, netOpening=O-RO, and heldLiability=netOpening+netReceipts-netRefunds-netDeductions. Every total is an arbitrary-precision fixed-two-decimal string and may exceed one entry's NUMERIC(14,2) ceiling. History retains all original entries and reversal links. A reversal is not a second cash event.

Compute totals and history/count in one repeatable-read snapshot over the whole ledger, independent of page size. For date-filtered movement reports expose signed opening/cash/deduction/correction buckets and the chosen date basis. Never call a filtered movement sum the current held balance. The balance response always identifies its as-of posting cutoff. Rent revenue and expenses exclude deposit receipts, refunds, openings and deductions; a deduction remains a liability release with unclassified destination, not declared rental revenue.

## DRE-02 mixed bank transfers and coordination with Payment

The first unit explicitly does not support splitting one incoming bank transfer between rent and deposit. A matching identity in the other stream rejects posting with a clear instruction to resolve the transfer externally; do not suggest fake suffixes or accept the same cash twice. Supporting mixed transfers later needs one verified transfer amount and bounded uses, with a separate design review.

Use exactly the existing Payment identity normalization: trim, bounded strings, case-sensitive equality on receivingAccountKey plus externalReference. Do not casefold only one stream. A deposit bank receipt requires both fields. These are operator-entered identities; account labels need actual configuration/facts before an operator claims they identify a real receiving account. No fabricated bank number is seeded.

A dedicated transaction advisory gate for incoming bank identity changes serializes the cross-stream check. At this scale a single fixed gate is simpler than a new transfer registry. Every Payment mutation and every deposit review/financial command acquires it before entity row locks. This deliberately serializes these low-volume command paths so a trigger cannot discover a needed bank gate only after the caller already locked a lease or payment. Existing active managed PENDING/CONFIRMED Payment identities block deposit receipt. An unreversed managed deposit RECEIPT identity blocks a new active Payment identity. A reversed/cancelled rental payment or reversed deposit receipt releases its identity according to the existing rental policy. No deposit-only override bypass exists. Legacy bank identities lack verified fields and remain outside this automatic claim, visibly unverified.

The additive integrity migration must cover Payment as well as DepositEntry with trigger-enforced cross-stream rejection. Install BEFORE STATEMENT triggers for INSERT/UPDATE/DELETE on Payment and managed deposit entry/account writes that first acquire the existing SHARED source gate, pg_advisory_xact_lock_shared(73422193), and only then the incoming-bank gate, before PostgreSQL reaches affected row locks. This source-before-bank order applies to supported direct SQL as well as application services. Never let a statement trigger take bank first and reach the existing source gate later in a row trigger. Row triggers then validate identity, aggregate balance and joined rules. A BEFORE ROW trigger alone is insufficient for UPDATE because its target row may already be locked. Apply the statement trigger unconditionally, including cash and legacy mutation attempts; services must therefore take this gate on all corresponding mutation paths before any entity lock. Direct SQL must not be allowed to take an entity lock manually and later enter these writes in reverse order; application-supported commands use the prescribed transaction entry, and deadlock/serialization failures of unsupported manual sequences must roll back without partial posting. Preserve the existing Payment partial unique index and all allocation/receipt invariants. Do not implement a service-only cross-check. Schema snapshot isolation and trigger command snapshots need actual independent-connection race tests; merely taking an advisory lock does not prove fresh visibility. If the implementation cannot demonstrate correct visibility at READ COMMITTED, use bounded SERIALIZABLE retries and prove one committed result rather than asserting correctness from SQL syntax.

This is a bounded material change to Payment integrity and requires its own independent financial review and full existing payment regression tests. Main must sequence it after the current frozen payment/receipt baseline. No Payment implementation writes are delegated by this document.

## Lock order and atomic posting

The agreed order is source gate, current actor authorization, actor/command advisory identity, incoming-bank gate for every Payment/deposit mutation, Lease row, DepositAccount row, original reversal target, evidence rows, monthly document counter. Category locks belong to Expense and are never acquired here. Every Payment mutation path must acquire the same bank gate before its existing lease/billing-period/invoice/payment locks. Acquiring a bank gate only from a Payment INSERT trigger after the service took a lease lock is insufficient; update the service order and verify it. Direct SQL triggers must follow compatible order or reject unsupported operations before partially taking conflicting locks.

After locking, reread lease state, review digest, account version, evidence availability and exact ledger sum. Require expectedVersion for all entry/review commands. Compute effects with Decimal/NUMERIC, reject negative liability and insert one entry, snapshot, audit, account increment and command in the transaction. Audit/command/counter/evidence errors roll back all database writes. Bounded retries reuse the same key/body. No automatic new command key follows an uncertain response.

Snapshot includes actual lease/tenant/room identity, exact amount, method-specific operator statements, occurrence/posting time, issuer operator name/id, event kind, document number and original target when correcting. Do not invent a legal issuer, tax ID, verified receiving account or tenant address. PDF uses shared supported font routing and existing Thai invoice/receipt conventions, repeated cancellation/correction markers and exact strings. The original snapshot stays immutable; later reversed state appears separately on every rendered page, as of the read. Documents say deposit record and disclose missing legal issuer facts; they are not represented as verified statutory/tax receipts.

## Private evidence implementation dependency

Implement a bounded ADMIN-only upload under `src/server/evidence`, separate from deposit arithmetic. Accept at most 5 MiB after decoding, PDF/JPEG/PNG only, with extension-independent magic validation and safe raster/PDF structural checks. Reject HTML, SVG, executable/polyglot content detected by the validator, malformed files and unsupported encryption. Do not promise malware freedom from MIME sniffing. Do not render uploaded content inline; authenticated download uses attachment disposition, nosniff and no-store. Preview, if added, needs a separately sandboxed conversion path.

Generate a random server storage key under ATTACHMENT_DIR, never use originalName as a path. Reject symlinks/non-regular files and path escape. Stream to a private exclusive OS temporary file with a hard byte limit and SHA-256. After admission, copy into a private exclusive destination temporary name under the attachment volume, fsync, and atomically rename to its unique final key before the transaction creates Attachment lease metadata, DepositEvidence and audit. Do not assume an OS temporary directory and Docker volume support cross-filesystem rename. If DB fails, an unreferenced file can remain and must never satisfy an evidence query. Do not delete an accepted file because an entry failed later. A maintenance inventory may report unreferenced files; automatic deletion and retention expiry are absent in this unit. Existing upload fixture paths must never count as proof of live upload.

Use these explicit initial technical defaults: at most 5 MiB per file, at most 10 admitted upload attempts in any rolling 10 minutes per ADMIN actor, one active upload per actor, and a 5 GiB total retained attachment-volume ceiling including accepted files, orphans and destination partial files. They are configurable positive deployment limits, not guessed legal retention rules. Before reading upload bytes, use an actor-specific session advisory admission lock with a non-blocking acquisition; a busy actor receives a bounded retry response. Under that lock, count and atomically record admission through a dedicated AuditLog action, so process restarts and invalid-file attempts cannot evade the rolling limit. Hold the actor lock until upload completion/failure and release it in finally or connection teardown. Do not retain request body contents in the admission audit. Total storage admission is serialized under the attachment-publication gate: count actual regular retained files, include temporary destination/reservation bytes, and reject any operation that could exceed 5 GiB before copying. Also enforce the source temporary-input byte limit during streaming; accepted metadata alone is not a disk-capacity measure. Test two actors competing for the last available capacity and two simultaneous uploads by the same actor. Failed admissions cannot reserve capacity indefinitely. Disk exhaustion returns a bounded error and leaves no accepted metadata. At posting, validate same-lease accepted metadata, regular retained file, length and hash; metadata alone cannot authorize a deduction. Protect accepted files against application overwrite and unlink. File encryption at rest/key custody is an operational deployment fact; do not claim it exists from a Docker volume alone.

Uploads and backup need a new explicit shared consistency protocol; the existing source gate does not currently prove backup publication safety. Introduce a dedicated attachment-publication advisory key. The upload acquires the source gate, then this publication gate before touching the destination volume or committing metadata. Operations backup opens a dedicated real database session, acquires a SESSION advisory lock on the same publication key before its first attachment inventory and before calling exportSnapshot, and holds that session through database dump, file copy and final inventory. Its lock owner can be separate from the snapshot owner, but it must remain alive for that full interval. The current exportSnapshot in operations/database.mjs starts a child psql session with BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY, then pg_export_snapshot and inventory SQL. Do not insert an unverified transaction-level locking call inside that read-only transaction or accidentally change its two-value output parser. The intended sequence is publication-lock session acquisition and acknowledgement, attachment inventory, the existing separate read-only snapshot transaction, dump/copy/verification, snapshot close, then session unlock/close in an outer finally. Unlock/connection cleanup must also run when inventory, snapshot startup, dump or copy fails. On unexpected lock-owner connection loss, abort the backup and do not mark its archive verified. Neither backup session takes the source gate after publication admission. Prove the actual PostgreSQL role can acquire/release this session lock and that it excludes the upload transaction advisory lock with the same key; do not claim session-lock behavior from API names alone. Streaming and validation of the OS temporary input happen before taking this gate. Test and document backup timeout/admission behavior; do not claim the current backup already follows this protocol. Publish accepted metadata only after durable file retention, so a snapshot cannot contain a reference to unavailable bytes. Unreferenced regular final files from a failed metadata transaction are retained, included in backup file manifests, and reported as orphans separately from accepted evidence. They do not appear as accepted Attachment/DepositEvidence records or authorize posting. Destination partial files left after a crash likewise remain non-evidence and are inventoried/reported until an explicit maintenance operation resolves them. No automatic unlink runs in this unit. Restore must retain DepositEvidence references and Attachment hash/bytes and verify retained files before enabling posting. Extend inventory coverage and publication coordination without changing historical frozen SQL registry contracts.

Retain every accepted evidence file indefinitely in the first version, with no ordinary delete endpoint. This is a technical no-expiry default, not a legal retention opinion. Actual storage capacity, private access, encrypted offsite copy and restore verification are Go-Live evidence, not supplied facts. Missing them prevents a readiness claim but not local synthetic implementation.

## Interfaces and bounded ownership

Derive strict discriminated command/DTO types from Zod. Use UUID normalization, bounded strings, explicit offset timestamps and canonical positive decimal strings with no exponent/rounding. The account review accepts zero opening explicitly; financial entry amounts remain positive. Unknown fields and forged actor IDs fail.

```ts
reviewDepositAccount(actor, rawReview): Promise<DepositLedgerDto>
recordDepositReceipt(actor, rawReceipt): Promise<DepositLedgerDto>
recordDepositRefund(actor, rawRefund): Promise<DepositLedgerDto>
recordDepositDeduction(actor, rawDeduction): Promise<DepositLedgerDto>
reverseDepositEntry(actor, rawReversal): Promise<DepositLedgerDto>
```

Server ownership is `src/server/deposits/{contracts,domain,service,index,pdf}.ts`, `src/server/evidence`, strict `/api/v1/leases/[id]/deposits` read/review/receipt/refund/deduction routes, deposit-entry reversal/document routes and evidence upload/download routes. Require current ADMIN for writes, STAFF/ADMIN for reads, existing Origin/auth/body-bound controls, no-store errors and replay-safe UI. UI lives in deposit feature files with a focused lease-tab integration owned by Main. Do not overwrite active lease/payment/expense owners' files.

Main currently coordinates expense's additive schema reaching 39 tables. Deposit's five logical tables come later, provisionally reaching 44 only if no intervening model lands. Do not hard-code that count or migration timestamp until Main freezes actual schema. Main owns User/Lease relations, affected Payment integration and newest restore registry. Preserve SecurityDeposit, Expense and original Attachment bytes during migration. No concurrent Prisma writes or in-place modification of historical restore registries.

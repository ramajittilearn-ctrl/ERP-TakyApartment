## Existing runtime and constraints

The protected ERP layout resolves a real session through awaited Next cookies and passes the actor to `AppShell`. It still wraps other screens in `DemoProvider`. The current payments screen consumes `useDemo`, browser-only payment totals, QR, CSV, and a demo receipt print button. Replace this screen's demo path completely. Leave the shared provider for other existing screens.

Payment routes delegate to independently reviewed services. STAFF and ADMIN can read and create pending entries. ADMIN alone can confirm, cancel pending entries, and reverse a confirmed payment. Confirmation allocates the exact payment amount and creates one receipt atomically. Reversal cancels that same receipt atomically. There is no independent cancellation endpoint for an issued receipt. The UI must not pretend otherwise.

Payment DTOs preserve exact decimal strings and explicit versions. Balance DTOs include frozen room/tenant/lease labels, ISSUED or VOID status, final total, active paid, and collectible outstanding. They do not include invoice versions. Existing GET `/api/v1/invoices/{id}` provides the invoice version required by confirmation. Reading balance and invoice detail separately does not create an atomic snapshot; the server still checks versions, invoice status, and current balance inside the financial transaction.

The generic `src/features/live/workspace.tsx` request helper discards error codes and formats money through Number. Do not reuse it for payment commands or arithmetic. Import only browser-safe contracts from `@/server/payments/contracts` and `@/server/invoices/contracts`, never their server index or service modules. `src/features/live/contracts.ts` supplies the existing lease response schema. The payment-local transport owns fetch/envelope validation and preserves error code and HTTP status.

All lists are managed-only. Demo and unmapped legacy entries are excluded by the API, not hidden by a browser filter. A visible notice must explain that these lists cover managed payments only and do not represent imported historical balances. Labels for confirmed allocations and receipts come from frozen invoice or receipt data, never the current tenant assigned to a room.

## Compared sketches

Candidate A has one payments page with a paginated table, one create dialog, and one selected-detail panel. The detail panel owns confirmation allocations, receipt display, pending cancellation, and reversal confirmation. It keeps one mutation attempt alive while the user resolves a network failure. It uses existing Card, DataTable, Badge, Field, Button and Radix-backed Modal primitives. This fits existing invoice and live CRUD screens and avoids a new route structure.

Candidate B has separate payment create, payment detail, receipt, and confirmation pages with router-managed drafts. It gives deep links and a larger allocation workspace, but navigation makes uncertain command outcomes harder to preserve and introduces several screens for approximately 15 rooms. Choose A for this bounded unit. Dedicated receipt routes or operational print can follow after legal issuer facts exist. Candidate A must still paginate all list and allocation choices; the small room count does not bound invoice history.

Red-flag review: the page has one financial writer, the API. It has no optimistic balance mutation or parallel demo payment store. It does not add a generic command bus, new cache library, payment repository, or one-file-per-fetch wrapper. Read-only display and form helpers stay within the payment feature.

## User flow

### Entry and list

The payments server page resolves the current session using the existing cookie/session convention and redirects unauthenticated access. Pass only `{ actorId: actor.id, admin: actor.role === "ADMIN" }` into `PaymentsScreen`. The actor ID scopes volatile recovery state and is not authentication proof. Role is a UI affordance; every API request still authorizes against the current database user. Do not serialize session tokens or private user fields.

On entry, load the payment page and non-demo lease options independently in parallel. Use GET `/payments?offset=0&limit=50` and GET `/leases`. Parse the existing lease schema, excluding demo leases and demo tenants. Do not impose an ACTIVE-only financial rule that the payment domain does not have. Current lease labels may label the selector, but label them as current lease information. Do not use them to rewrite historical invoice labels.

The list displays actual received date and time in Asia/Bangkok, internal reference, lease identity, method, exact amount, status, and receipt number if present. Statuses have explicit Thai text for PENDING, CONFIRMED, CANCELLED and REVERSED. The status filter and optional lease filter are server query parameters. Changing a filter resets offset to zero. Previous and Next use offset/limit; there is no total count in the API, so do not invent one. Disable Next when fewer than limit rows return; an empty extra page permits Previous. Do not claim a current page search or total is an all-history report. Remove the unsupported demo month/search/CSV/QR controls.

Selecting a row fetches its current GET detail. Paginated results and replay responses are not authoritative current detail. Show loading, empty, and read failure states separately. A refresh button reloads the current page and selected detail without clearing a pending command attempt.

### Record a pending payment

STAFF and ADMIN have the same entry form. Select a non-demo lease, exact amount, actual received date/time explicitly labelled Bangkok UTC+07:00, and CASH or BANK_TRANSFER. CASH shows no bank identity fields and sends neither field. BANK_TRANSFER requires a traceable external reference and receiving account identifier, labelled as an operator-entered identifier rather than a verified bank account. Never fabricate a bank option or legal identity. Blank fields prevent submit. There is no slip upload, QR, automatic bank verification, deposit entry, refund, or post-VOID exception control.

The selected lease's balance list can help the operator inspect existing invoices. It must not auto-allocate or imply a pending entry settles them. The create operation remains available for a non-demo lease even if its current payable invoice list is empty, matching the accepted API. Explicitly state that this records funds pending review, creates no receipt and cannot confirm without eligible invoices. Do not label such a pending entry as a resolved post-VOID exception or credit facility.

Use a text amount input with decimal input mode, not floating-point number coercion. The operator may type `1` or `1.2`; before review normalize these lexical forms to `1.00` or `1.20`. Reject signs, commas, exponent notation, leading-zero ambiguity, zero, more than two fractional digits, and amounts beyond the API's 12 integer digits. Never round extra digits. Keep the canonical value in the reviewed command.

Convert a validated datetime-local wall value directly into an offset-bearing ISO string with `+07:00`. Do not call `new Date(localText)` and inherit the workstation timezone. Validate real calendar dates and time fields; round-trip UTC components with the fixed seven-hour offset or use an existing safe helper. Defaulting to Bangkok now is allowed only on opening a new form. Retrying freezes the originally reviewed timestamp. Do not invent a future-date prohibition absent from the accepted domain.

The final button says record pending payment. Show the reviewed amount, method, lease and received time before submission. Success means the server accepted the pending record, not that settlement or bank verification occurred. Reload current detail after success; the command's response can be an older replay result.

### ADMIN confirmation and exact allocations

For a freshly loaded PENDING payment, ADMIN can open confirmation. Load all balance pages for that payment's lease with limit 100, stopping at a short page and respecting the endpoint offset bound. If history exceeds the bound or any page fails, show a recoverable error instead of silently treating a partial list as complete. Filter selectable invoices to ISSUED with positive outstanding. Show VOID and zero-outstanding history as nonselectable only if shown at all. No cross-lease selection.

For each selected invoice, fetch current GET invoice detail and retain its version. Fetch selected details concurrently. Require managed, matching lease, ISSUED, and non-null frozen labels/final total. Match its identity and final total against the balance entry. If status or identity differs, invalidate that selection and require refreshed balances. This is read-side validation for clear feedback, not a replacement for transaction checks.

Show invoice number, frozen room and tenant labels, final total, active paid, outstanding, and an explicit allocation input per selected invoice. The operator chooses every allocation; never silently auto-distribute. A per-row fill-outstanding button is an explicit action. The exact sum must equal the payment amount and each allocation must be positive and no greater than the displayed outstanding. At most 100 distinct invoices may be submitted. Show exact allocated and remaining amounts throughout. Disable final confirmation while invoice versions are loading, allocations are invalid, or the full reviewed summary has not been presented.

Send the current payment version plus the retained invoice versions. A confirm dialog states that confirmation issues a receipt and updates collectible balances. On success fetch payment detail and GET receipt by receipt ID, and reload affected balances and the payment list. The receipt ID is not the payment ID.

`CASH_DUPLICATE_REVIEW_REQUIRED` keeps the pending payment and allocation draft visible. Explain the server's heuristic, same lease, amount and Bangkok day as an existing confirmed cash payment. The API does not return candidate identities; do not invent them. The ADMIN may abandon or explicitly enter a trimmed 1 through 1000 character override reason after manual review. This changed body starts a new deliberate command key. The exact bank-reference conflict has no override path. Do not treat a duplicate warning as a successful confirmation.

### Details, cancellation, reversal and receipt

All roles can view current payment metadata, recorded/confirmed/cancelled timestamps and actor IDs where returned, bank identity, retained allocations, receipt link, and reversal reason. Do not invent staff display names from IDs. Pending records explain that they contribute no confirmed income and have no receipt.

ADMIN may cancel only PENDING with a required reason and expected payment version. This is distinct from closing a dialog. ADMIN may fully reverse only CONFIRMED with a required reason and expected version. The reversal confirmation shows the exact original amount and warns that all allocations will cease to count and the original receipt will be marked cancelled. No partial reversal, delete, edit, receipt number replacement or separate receipt cancellation button exists. REVERSED and CANCELLED are read-only terminal states. After either action, refresh current detail and balances. On reversal refresh the same original receipt.

Receipt view uses only `ReceiptDto.snapshot` for original amount, payment method, actual received time, issuance time, issuer user snapshot, receipt number and per-invoice frozen labels/amounts. Display cancellation as an additional clearly labelled banner with reason, actor ID and time. Preserve the original content and original receipt number. The server verifies the snapshot fingerprint; do not turn a mismatch error into an empty or reconstructed receipt. Show the fingerprint as an optional integrity detail, not proof of legal validity.

This unit provides an authenticated receipt record view. It supplies no print, browser PDF, download or operational legal invoice wording. Remove the old demo print action. The screen may say that legal receipt printing is pending issuer configuration. Do not use demo property settings as a legal issuer.

## Transport, types and state

Use existing `{data}` envelopes and response schemas. Payment and balance list schemas can be composed locally from the existing item schemas, literal `managed-only` scope, and nonnegative integer offset/positive bounded limit. Existing schema definitions remain authoritative. GET and POST use same-origin fetch, `cache: "no-store"`, JSON content type for bodies, and normal same-origin session cookies. Do not set a forged Origin or trust a browser role. Preserve server code, message and HTTP status in a payment-local `PaymentApiError`. Parse unknown JSON through Zod. Unexpected HTML, malformed JSON, or schema mismatch is a failed/uncertain response, never a successful mutation.

A small module sketch is sufficient:

- `screen.tsx` owns filters, current selection, form action and request lifecycle. Export `PaymentsScreen({actorId, admin})`.
- `client.ts` owns typed `paymentRequest({path, schema, method?, body?, signal?})` and `PaymentApiError`. It imports contracts, not server implementations. It preserves error codes and parses envelopes once.
- `form.ts` owns lexical money normalization, exact minor-unit conversion, explicit Bangkok wall-time conversion, and command attempt construction. It has no fetch, React, DB or ambient clock reads. Pass now explicitly if required.
- `journal.ts` owns one actor-scoped volatile mutation attempt, its settlement and subscriptions across payment route unmounts. It has no browser storage or server imports.
- `receipt.tsx` renders immutable receipt fields and cancellation metadata.
- `screen.module.css` adds only feature-local responsive layout. Existing shared primitives remain unchanged.

Small local components may stay in screen.tsx rather than adding a wrapper per input. Derive command and DTO types with schema inference. Model the form action as a discriminated union, create, confirm with payment and versioned invoice selections, cancel with payment, or reverse with payment. Model a submitted attempt as immutable `{key, operation, body, state}` where state distinguishes submitting, uncertain and rejected. Store the exact serialized JSON body and key together. Do not have independent busy booleans that permit two mutations at once.

Money parsing uses digit strings to BigInt minor units. All comparisons, sums and subtraction use BigInt. Format canonical decimal strings by grouping their whole digits and preserving exactly two fraction digits. Do not use Number, parseFloat, Intl numeric conversion, demo money helpers or Prisma in the browser. JSON payloads contain decimal strings, never BigInt. Date formatting uses explicit Asia/Bangkok; calendar due dates remain date-only.

Maintain one attempt in the feature-local `journal.ts` client module, outside component lifecycle. Bind the journal to the server-supplied actor ID before showing or retrying an attempt. A different actor ID clears the previous attempt and increments a generation token. A synchronous journal lock prevents double-click races before React rerenders. Generate `crypto.randomUUID()` once when the operator submits a reviewed mutation. Retry the identical frozen body and case-preserved key after network uncertainty or server 500. Never regenerate the key automatically on retry or recalculate receivedAt/versions. Do not auto-retry financial commands in an effect. A new key is allowed only after a definitive rejection and an explicit revised submission, or after the prior outcome was reconciled. Refresh payment detail after a successful replay because its stored response may describe earlier state.

The immutable attempt owns `{actorId, generation, operation, path, key, serializedBody, state}`. The journal, not the React screen, owns the submitted POST promise and its completion. Component cleanup unsubscribes the view but does not abort POST or delete the attempt. The promise updates journal state only if actor/generation still match. Completion stores its parsed result or uncertain/rejected outcome even if the payment route is unmounted. On return the screen subscribes, restores the recovery panel from the same module instance and actor, and fetches current payment detail when its known outcome allows it. Same-origin Next Link navigation and Back/Forward therefore do not discard the only key. No route navigation interceptor or unsupported Next router blocking API is required.

Confirm, cancel and reverse keep paymentId in path/attempt metadata only. Their strict HTTP bodies omit paymentId and contain commandKey plus the existing non-identity fields. Derive body types from the authoritative domain schema shapes with paymentId omitted, respecting the refined confirm schema restriction documented in the API contract. Do not serialize the full domain command directly. Create sends its existing complete create body. Preserve the exact path and body together during retry.

Closing a modal leaves an unresolved attempt in the page recovery panel. While unresolved, disable another payment mutation, keep the draft frozen, and offer retry of that exact attempt. GET success alone cannot prove an uncertain create was the same intended command; do not clear it based on a similar amount/reference row. The module retains an unresolved attempt during same-document navigation even though its panel is only visible on Payments. Subscribe a global beforeunload listener while the journal has an in-flight/uncertain attempt, independent of React route mount. It warns before leaving/reloading the document. Its lifetime follows journal state rather than component cleanup.

Existing AppShell logout sends POST `/api/auth/logout/` and, on success, calls `window.location.assign("/login/")`. Existing login also performs a full document navigation. A module-owned pagehide listener clears the journal and increments its generation on every document exit, including back-forward-cache entry, so a restored document cannot resurrect financial bodies after logout. Explicit logout intentionally discards its volatile recovery state; it does not cancel or roll back a server transaction. A failed logout leaves the journal intact. Each 401 command/read response clears actor-bound sensitive state and directs the user to login, while preserving a generic warning that prior disconnected work needs reconciliation. The generation fence prevents a late response from restoring cleared state. Before any mounted payment view displays recovery, it checks actorId equality again. No journal state is shared between tabs or users.

This strategy covers existing app login/logout and route navigation without editing shared lifecycle files. A forced reload or full document exit still discards the journal after its browser warning, and payment data might already have committed. Tell the operator to inspect persisted records before recording funds again. Do not claim durable retry recovery across reload, a new tab, a browser crash, or session changes performed outside the app's authenticated flows. Do not persist bank references, bodies, tokens or tenant details in localStorage/sessionStorage. If shared authentication/navigation behavior changes to same-document account switching, Main must assign a lifecycle integration change before enabling it.

Read requests use AbortController and a selection/filter generation guard so an older response cannot replace a newer one. Independent entry reads and invoice detail reads run concurrently. Derived totals stay derived from draft state. Keep financial transitions in click/submit handlers. No cross-user or persistent client cache is introduced.

## Error recovery and accessibility

On 401, stop mutations, clear actor-bound volatile state as specified above, and offer login after explaining the session expired and any prior uncertain outcome. Do not create a fresh command after authentication automatically. On 403, remove privileged actions after refreshing session/page state, retain the result as unconfirmed if it was uncertain, and explain insufficient permission. A server rejection does not prove a previous disconnected attempt failed.

On STALE_VERSION, PAYMENT_STATE, ALLOCATION_EXCEEDS_BALANCE or INVOICE_NOT_PAYABLE, show the code and clear next-step guidance, refresh current payment/balances, and require the operator to review and resubmit a new intent. Never silently update versions or reallocate. On IDEMPOTENCY_CONFLICT, stop and preserve the attempted body/key for manual reconciliation; do not fall back to a new key. On snapshot mismatch or sequence exhaustion, disable confirmation/receipt presentation as appropriate and show an actionable operator error. Keep form values on 422 and bank-reference conflicts. No sensitive request bodies or bank identifiers enter console logs.

Every input has a visible label, unique id and associated hint/error. Shared `Field` already creates an associated label/id and hint via `useId` and `cloneElement`. Reuse that behavior for its direct input child. For repeated allocation controls give each Field a distinct invoice-labelled name. Inline errors need an associated description as well; if the existing Field hint replaces aria-describedby, render the relevant hint and error together rather than assuming both IDs survive. Do not change shared UI. Every Modal must receive an explicit persisted-data description because its current default says changes are demo-only. Dialogs have distinct accessible names, keyboard focus containment and return focus through the existing Radix primitive. Do not nest a second dialog inside an open one. Confirmation steps can replace the dialog's content. Pending command recovery remains reachable by keyboard after close. Announce success through role=status, errors through role=alert, and mark loading regions aria-busy. Give repeated allocation controls labels containing invoice number. Text accompanies status colors. At narrow widths preserve full money values and usable action buttons with an explicitly labelled scrollable table region.

## Acceptance and evidence

Before integration, execute focused helper/transport tests, typecheck, lint, formatting, full unit tests, build or supported route type generation, and actual browser cases against a new isolated synthetic database. Main supplies attested ports, Docker project and DB identity. Do not alter ports 3700/3701, existing databases, F11 target/proxy/nonce guards, or another session's evidence. Screenshots and browser logs must survive failed runs. An independent reviewer examines the integrated code and verifies corrections.

Required browser behavior:

1. STAFF records a BANK_TRANSFER pending payment with explicit receiving account/reference and Bangkok timestamp. Reload persists exactly one entry. No receipt, confirmation, cancellation or reversal action is available to STAFF. Both STAFF and ADMIN can read persisted managed details.
2. ADMIN records CASH with no bank identity. Exact input `0.10` plus `0.20` allocations totals `0.30`, and the maximum supported amount displays without loss. Extra precision, zero, exponent and cross-lease allocations are rejected before POST.
3. ADMIN explicitly allocates one payment across two invoices on the same lease. Confirmation persists exactly one receipt, correct exact balances and retained frozen labels. Partial payment remains payable; a later payment can settle the remainder. Nothing uses current room tenancy for historical labels.
4. A real direct navigation and keyboard-only dialog flow has labels, focus return, announced errors, no demo description, usable narrow viewport and no hydration/browser console errors. Managed empty list differs from failed fetch. Paginated payments and more than 100 balance history rows do not silently hide choices or claim a total.
5. Create and confirm are double-clicked and their response is deliberately dropped after the server commits. Exact retry uses the same key/body and yields one payment/receipt. Closing/reopening retains the uncertain recovery panel. Navigate away with an actual AppShell Next Link while the response is lost, use browser Back/Forward, and verify exact retry still uses the original body/key and one persisted payment/receipt. Repeat with the POST settling while the page is unmounted. Successful logout followed by login as another user must expose no old attempt; browser Back must not resurrect its body, and late promise completion must not restore cleared state. A replayed historical DTO is followed by current GET. Reload warning appears only during unresolved/in-flight commands.
6. Two ADMIN sessions race allocations. The loser sees the actual stale/balance error, retained draft and refreshed values. It cannot silently reallocate, refresh versions and confirm. Duplicate cash prompts manual reason and a deliberate new command; bank duplicate never exposes an override.
7. ADMIN cancels pending with a reason. ADMIN fully reverses confirmed with a reason. Persisted balances restore exactly; receipt view shows its original number/snapshot plus linked cancellation. Terminal records have no editable action. No separate receipt cancellation, QR, CSV, print, upload, refund, exception or deposit capability is falsely advertised.
8. Expired session, disabled/demoted ADMIN, malformed response, slow selection switches, receipt fingerprint mismatch, unavailable API and failed allocation page each produce recoverable UI states without a false success, sensitive logs, stale detail overwrite or a newly generated retry command.

Transport interception may reproduce response loss or delay while real financial requests still reach the actual isolated app/database. Interception is not a substitute for persisted invariant checks. Record exact browser commands, observed counts, evidence locations and limits. Actual legal receipt facts, private evidence policy, historical mapping, post-VOID resolution, Owner UAT and Go-Live remain later gates under the existing project backlog.

## Existing flow and alternatives

The current `/expenses/` page renders `ExpensesScreen`, which reads and writes the in-memory demo provider and exports demo rows. It has no persisted entry point or actual mode selector. The payment page authenticates on the server and passes actor ID and ADMIN capability into its client screen. Its feature-local journal owns a frozen command across client route navigation, including uncertain results. Expense services own monetary precision, lifecycle transitions, authorization, idempotency and current totals. The UI must consume those decisions rather than duplicate them.

Two complete shapes were considered:

1. Add live branches to the existing demo screen and reuse its demo draft, number totals and client CSV exporter. This has fewer files but creates two meanings for amount, status and category in every handler. It makes an apparently harmless demo helper change affect persisted money. Reject this shape.
2. Keep the demo component intact and add an authenticated expense-specific persisted screen with a small transport module and journal. The page selects the persisted screen by default. An explicitly labeled expense-local demo selector mounts the existing demo screen independently. No demo entity or total enters a live request. Select this shape.

The selected design keeps one owner for each state. The journal owns command execution and replay. The screen owns filters, drafts and selection. Server contracts own DTOs and policies. No generic financial UI framework, shared payment journal modification or new global workspace provider is required. Direct imports of client-safe expense contracts are allowed; importing the server index would pull Prisma into the client and is prohibited.

## User flow

After authentication, the operator opens persisted expenses, chooses a property, reviews the full-result approved OPEX/CAPEX totals and pages through filtered rows. Either STAFF or ADMIN can prepare a pending entry. Only ADMIN sees approval, cancellation, reversal and global category management controls. The server remains the authority after a role change.

The new-entry dialog asks for property, active category, description, vendor, amount, occurred date, CASH or BANK_TRANSFER, and optional note. The amount control uses decimal text, preserves satang and rejects exponent notation or excess precision. It may normalize `1` to `1.00` and `1.2` to `1.20` by string operations only. It never rounds, calls Number for money or rewrites the calendar date through a timezone. Date wording identifies the operator-entered expense date; no bank reconciliation or closed-period policy is implied.

Saving creates PENDING even for ADMIN. Posting is a separate explicit confirmation that displays the immutable entry and its version. The possible-duplicate count is a non-blocking warning, never proof of a duplicate or an invented override requirement. Pending entries cannot be edited; cancel and prepare a correction instead. A correction action exists only on CANCELLED or REVERSED entries and carries their ID and property into a new pending draft. Reversal asks for a reason, states that it corrects recorded expense history and does not record a cash refund, and cannot itself be reversed.

The detail dialog displays frozen category name/kind, original amount/date/vendor/method/note, status/version, recorded actor ID/time, applicable posting/cancellation/reversal actor IDs/times/reasons and correction link. These DTOs contain actor IDs rather than display names; do not invent names or issue one lookup per row. Referenced corrections can open their managed detail. The API does not provide reverse lookup of all correcting entries, so do not claim an exhaustive correction chain.

Category administration lists all global categories, including inactive ones. ADMIN can create a name and fixed OPEX/CAPEX classification and activate/deactivate an existing category with its expected version. Explain that these categories apply across properties. Name and kind are immutable; no rename or reclassification control exists. Capture lists only active categories, but history filters include inactive categories. If deactivation races posting, refresh and show the actual server result.

## Exact existing requests and responses

All paths below follow the application's trailing slash convention. JSON success is `{ data: T }`; errors are `{ error: { code, message } }`. Reads and mutations use same-origin credentials and `cache: no-store`. Fetch requests validate unknown JSON at the feature boundary with existing Zod contracts. Export alone returns CSV.

| Method and path | Exact request | Success data |
| --- | --- | --- |
| GET `/api/v1/properties/` | No query required | Array parsed with existing `propertySchema`; use for labels and selection |
| GET `/api/v1/expense-categories/` | No query | `CategoryDto[]` |
| POST `/api/v1/expense-categories/` | `name, kind, commandKey` | `CategoryDto`, HTTP 201 |
| POST `/api/v1/expense-categories/{id}/active/` | `active, expectedVersion, commandKey`; ID only in path | `CategoryDto` |
| GET `/api/v1/expenses/` | Optional `propertyId, from, to, kind, categoryId, status, query`; `offset` default 0, `limit` default 50, max 100 | `ExpenseListDto` |
| POST `/api/v1/expenses/` | `propertyId, categoryId, description, vendor, amount, occurredAt, method, commandKey`; optional `note, correctionOfId` | `ExpenseDto`, HTTP 201 |
| GET `/api/v1/expenses/{id}/` | ID only in path | `ExpenseDto` |
| POST `/api/v1/expenses/{id}/post/` | `expectedVersion, commandKey` | `ExpenseDto` |
| POST `/api/v1/expenses/{id}/cancel/` | `expectedVersion, reason, commandKey` | `ExpenseDto` |
| POST `/api/v1/expenses/{id}/reverse/` | `expectedVersion, reason, commandKey` | `ExpenseDto` |

`CategoryDto` is `{ id, name, kind: OPEX|CAPEX, active, version }`. Derive client types from `categoryDtoSchema` and `expenseDtoSchema`. `ExpenseDto` is a status-discriminated union. All variants have `id, propertyId, categoryId, description, vendor, amount, occurredAt, method, note, categoryName, categoryKind, version, possibleDuplicateCount, recordedById, createdAt, correctionOfId`. POSTED adds `postedById, postedAt`. CANCELLED adds `cancelledById, cancelledAt, cancelReason`. REVERSED contains posting fields plus `reversedById, reversedAt, reverseReason`. PENDING has no transition fields. Narrow by status; do not manufacture nullable lifecycle fields or cast DTOs.

`ExpenseListDto` contains `scope: managed-only`, `items`, `offset`, `limit`, `total`, `excludedLegacyCount`, and `totals: { opex, capex, total }`. Totals are exact decimal strings over all matching POSTED rows, not the displayed page. Their response schema must accept nonnegative two-decimal aggregate strings beyond the single-entry NUMERIC(14,2) ceiling. Do not reuse `expenseMoney` for aggregate sums. All selected predicates, including status, apply. Thus selecting PENDING produces zero approved totals. Label these totals "ค่าใช้จ่ายที่อนุมัติแล้วตามตัวกรอง". Do not sum formatted page values. The legacy count applies to the selected property, or all properties if none is selected; it is not filtered by date, status, kind, category or search. State that scope beside the exclusion notice.

Filters serialize once through the same normalized object for list and export. Empty controls omit their keys. Unknown/duplicate query keys, reversed date ranges and invalid pagination remain errors. Changing any predicate resets offset to zero. Responses carry their request generation; a late prior filter/detail response cannot replace the selected result. While loading a different filter, hide or clearly mark old totals/rows as stale and disable export until that filter is loaded. Categories and properties load concurrently without loading tenants, leases or rooms. A category creation only refreshes categories; an expense mutation refreshes current list and selected detail without a full page reload.

## Command execution and recovery

Use an expense-local module journal modeled on the accepted payment journal, with operation-discriminated result types for expense versus category. Its public use is `bindExpenseActor(actorId)`, `subscribeExpenseJournal(listener)`, `expenseJournalSnapshot(actorId)`, `submitExpenseCommand(command)`, `retryExpenseCommand(actorId)` and `dismissSettledExpenseCommand(actorId)`. The command contains actor ID, operation, path, original key and serialized body. One journal attempt can be unresolved at a time across expense and category dialogs.

Create the key once immediately before first dispatch. Synchronous journal registration blocks double-clicks before React updates. Freeze the exact body, path and key for retries. The journal owns the promise across route unmount. Abort outdated reads, but do not abort a financial POST merely because a dialog closes or the user changes menus. On remount, show its settled or unresolved state. Never silently submit a new key for an uncertain result.

A network failure, invalid success envelope or server failure sets sticky `mayHaveCommitted`. A later 403, 409 or 422 response cannot erase that uncertainty and enable a new command. An initial definite client rejection can retain the draft for correction; a stale-version rejection requires loading and reviewing current detail before generating a replacement command. IDEMPOTENCY_CONFLICT stays blocked for reconciliation. Successful replay can return its original historical DTO; refresh current detail/list before presenting current actionable versions.

Recovery controls render inside the active Modal so Radix does not make them inert or aria-hidden. With no modal, render recovery on the page. Explain that the command survives client menu navigation in this tab but not reload/tab close. Add the same beforeunload protection and pagehide/actor generation fencing as payments. Explicit logout and account changes clear sensitive journal state; late results cannot cross actors. Do not store bodies in localStorage or sessionStorage. A full reload with an unresolved command requires checking persisted records before a new capture; do not claim durable recovery beyond this tab lifecycle.

Current permission denial hides/blocks privileged actions and refreshes the authorization state where available. A 401 follows the existing login/reconciliation behavior. UI capability flags are convenience only; endpoint checks and current database authorization remain mandatory.

## Bounded server CSV proposal

This endpoint does not exist at the backend baseline. Implement it only after independent acceptance of this section. Prefer one authenticated server export over accumulating pages in the browser, which can mix revisions and omit rows.

Add GET `/api/v1/expenses/export/`. Its strict filter schema derives from `expenseListInput` with offset and limit omitted. It accepts exactly `propertyId, from, to, kind, categoryId, status, query`. A distinct static route prevents the dynamic detail route from interpreting `export` as an expense ID. Require current authenticated STAFF/ADMIN, return no-store, and preserve normal JSON errors before any CSV bytes are sent.

The service call is `exportExpenses(actor, unknownFilters): Promise<ExpenseExportDto>`. Its server-only DTO contains `scope: managed-only`, normalized filters, generatedAt, excludedLegacyCount, totals and all matched ExpenseDto rows in the same order as list. Share the pure predicate builder with list to prevent divergent filtering, keeping the current public list API unchanged. One RepeatableRead transaction authorizes, counts, loads rows, and calculates totals/exclusions. The export bound is 10,000 matching managed rows. If count exceeds it, reject HTTP 422 with `EXPORT_TOO_LARGE` and an instruction to narrow filters. Never truncate, return only the first page or begin a partial download. Fetch in a bounded query under that transaction; no browser loop or per-page transactions. Mark `generatedAt` as export generation time, not an accounting close timestamp.

Use a pure CSV formatter and a fixed, rectangular column schema. Include one `recordType=summary` row even for zero matches, then one `recordType=expense` row per match. The columns are `recordType, scope, generatedAt, filtersJson, excludedLegacyCount, approvedOpex, approvedCapex, approvedTotal, id, propertyId, categoryId, categoryName, categoryKind, status, version, description, vendor, amount, occurredAt, method, note, possibleDuplicateCount, recordedById, createdAt, correctionOfId, postedById, postedAt, cancelledById, cancelledAt, cancelReason, reversedById, reversedAt, reverseReason`. Summary-only fields are blank on expense rows except scope and generatedAt. Expense-only fields are blank on the summary row. Unavailable lifecycle fields are empty, never fabricated values. Summary totals describe the same filters, and metadata states that later reversal restates the current expense view for the original occurred date. Include this correction meaning in the UI export notice and `filtersJson` metadata as a distinct `viewSemantics` value rather than pretend it is a request filter.

Return UTF-8 with BOM, CRLF records, standard doubled quote escaping and `Content-Type: text/csv; charset=utf-8`. Always quote cells. Neutralize spreadsheet formula prefixes in untrusted text with an apostrophe before escaping, including `=`, `+`, `-`, `@` after leading whitespace/control characters. Quote escaping alone is insufficient. Test vendor, description, category, note and reason fields with hostile fixtures. Preserve stored text unchanged. Money cells must preserve exact decimal strings; never convert them to JS numbers or formula expressions. CSV contains exact digits, but spreadsheet auto-detection may alter display; explain text-column import for exact large amounts. Set fixed safe attachment filename `expenses-YYYYMMDDTHHmmssZ.csv` using server time, never user text. This is a current managed ledger extract, not a tax document, period-close statement or proof of refund.

## File ownership and implementation sketch

The eventual isolated UI owner may change `src/app/(erp)/expenses/page.tsx`, add `src/features/expenses/{live-screen,client,journal,recovery,form}.ts[x]` and an expense-local CSS module, and add focused unit/browser tests. The current demo screen remains intact behind explicit selection. The page uses `requirePageActor()` and passes actor ID/ADMIN capability. Its client entry contains the live/demo selection and labels each mode before mounting its component. Switching mode cannot dismiss or replace an unresolved live command; keep recovery visible or block that switch with an explanation.

The CSV owner may add `src/server/expenses/export.ts`, `src/app/api/v1/expenses/export/route.ts` and export tests, and modify expense contracts/query/service/index only to derive the export filter and share predicates. Main must assign that ownership explicitly to prevent UI/backend concurrent writes. No schema, migration, inventory version, invoice/payment module, shared UI component or workspace provider change is needed for this increment. Main owns the small AppShell `/expenses/` classification change once the persisted page is integrated. Until that change, its global demo badge would be misleading; it is an integration acceptance item, not an ignored limitation.

Use explicit action variants such as `{ kind: create }`, `{ kind: post, expense }`, `{ kind: cancel|reverse, expense }`, `{ kind: categoryCreate }`, `{ kind: categoryActive, category, active }`, with each literal expressed as a TypeScript string in implementation. Derive request bodies from Zod inputs, omitting path IDs exactly as routes do. The screen never directly calls fetch for a mutation outside the journal. Keep money formatting pure and exact. Share no mutable state with payment capture, and do not refactor the accepted payment implementation in this unit.

## Inspected behavior

The service re-reads enabled current users and rejects stale role assertions before resolving an idempotent replay. Expense and category commands share an actor-scoped advisory-lock/key namespace. Row mutation, exact before/after audit data and immutable command result are in one transaction. Known serialization/deadlock retries are bounded.

Service mutations acquire the shared source gate and command lock, then category before expense. Category deactivation shares that category lock with posting. Expected versions and status are checked after locks. The reviewed race contract correctly permits posting followed by later deactivation with both commands committed, and requires posting to fail when deactivation wins first. Actual concurrency remains unverified until PostgreSQL tests run.

Managed expenses preserve original amount, property, category, description/vendor/date/method, flags, snapshots, creator and correction linkage. CHECK constraints require exact lifecycle provenance shapes. Reversal retains posting provenance and is terminal. Existing legacy rows remain null in managed metadata, immutable and excluded from managed balances. New default-true and explicit-true legacy INSERT shapes are rejected by the INSERT trigger. Category names/kinds and origin metadata are immutable; activation changes require current ADMIN provenance. Category snapshots are compared to the locked category on creation. No property-scoped category or nonexistent Property demo flag was introduced.

List rows, counts, duplicate warnings and POSTED-only grouped totals use one RepeatableRead transaction. SQL grouping covers all matching rows rather than only the returned page, and uses frozen category kind. Amounts remain Decimal or integer satang strings. Deposits do not enter the expense ledger.

Routes use authenticated actors, exact Origin checks on mutations, bounded JSON input, strict schemas, path-owned IDs, promised Next.js params, no-store envelopes and the existing sanitized error handler. Pure route tests use mocked service/auth boundaries and do not prove SQL authorization.

Payment confirmation's invoice cap checks reject an active NaN allocation, so this report does not assert that such a payment can settle an invoice. Main identified the same issue and will assign an actual PostgreSQL reproduction and a new additive payment migration. Do not edit or rewrite an already applied payment migration.

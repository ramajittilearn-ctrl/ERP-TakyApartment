# Deposit integrity and coordination acceptance matrix

These tests address independent findings DCR-03 and DCR-04. They are authored acceptance work, not a PostgreSQL pass. Main owns actual execution in the freshly attested candidate database. The first Core2 run exposed an unexpected serialization error shape; the separate safe probe must establish that shape before changing the bounded retry classifier.

The existing deposit suite now has thirteen cases after DCR-02. The new `deposit-integrity.test.ts` has twenty-four parameterized cases and `deposit-races.test.ts` has nine. The normal matrix therefore contains forty-six cases across those three files. `deposit-retry-probe.test.ts` is a separate diagnostic mode, not a substitute for their acceptance.

The shared core helper requires a loopback `taky_deposit_test_*` URL and attests actual database and role on every independent connection. All fixtures are synthetic, with real retained bytes and a dedicated core verifier. It makes no production upload, format-parser or backup-security claim.

Integrity cases compare full account, entries, commands, audits, counters, attachment/evidence metadata and retained-file hash after rejection. Four temporary protective fault triggers raise after audit, counter, command or entry writes; they never disable or weaken application guards and are removed in finally. The exact original command is retried after removal and replay must add no records. Current disabled/demoted actors cannot replay. All four reversal buckets preserve original document snapshot/hash through label changes. Negative-liability reversals reject. A finite authoritative raw receipt is the positive control; separate transactions test non-finite/sign amounts, cross-lease evidence, actor, sequence, snapshot/hash forgery, skipped account version and duplicate reversal.

Race cases use real independent PostgreSQL connections. A controlled holder takes source then bank admission in separate statements. Actual advisory waiters establish arrival order before two service claims or a READ COMMITTED direct Payment writer contend with a deposit receipt. Exactly one active cross-stream identity may remain. Deposit reversal and pending Payment cancellation release their identity while retaining history. Duplicate reversal and receipt-reversal/spend compare committed counts, versions, commands, audits and liability. Same-key reversal calls must return one result.

For source-close cases, the holder owns shared source and bank, an independent close transaction queues exclusive source, and direct/service writers start in both orders. The tests inspect actual lock state: both writers wait for shared source, have not obtained bank or tuple locks, and have written no records. The close transaction must acquire and release exclusive source before both valid writers complete. Different incoming identities permit both supported writes, with committed liability/audit/command checks. A timeout is failure, never the success condition.

No database, Docker, browser, build or privileged operation has been executed by the implementation agent. Scoped lint and formatting passed. An initial typecheck was blocked by the absent generated client after dependency restoration. Main regenerated this worktree own forty-four-model client; the corrected full typecheck now passes. The retry probe was corrected to supply its required synthetic email, then Main executed the actual probe and supplied the strictly allowlisted adapter shape described in retry-correction.md. The complete database acceptance matrix remains unexecuted by this agent.

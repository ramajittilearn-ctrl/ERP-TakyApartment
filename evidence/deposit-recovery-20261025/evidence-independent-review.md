# Independent evidence and validator review

Reviewed app evidence commit `8ee42ab` and validator commit `5ef6e36` on 2026-10-25. This reviewer did not implement either component. The coordinator-owned Prisma copy and the validator's uncommitted test-only Host-header correction were not staged or changed.

No actionable source defect was established in this review. The evidence API can proceed to UI integration against its documented transport. This conclusion is a source review, not Stage 3E acceptance or Go-Live approval.

## Scope and source conclusions

- `src/server/evidence/admission.ts` checks enabled ADMIN in PostgreSQL, takes a nonblocking actor-specific session advisory lock, records the admission before reading the body, and counts the dedicated audit action over the rolling ten-minute window. The session remains open through the callback. Connection loss aborts work; cleanup closes the session. `contracts.ts` defaults to ten attempts, one active operation through the lock, a 5 MiB file ceiling and 5 GiB retained capacity. Lease UUID input is normalized before use in admission audit metadata.
- The upload route uses the existing genuine stored-session lookup and Origin comparison. It rejects STAFF, compressed bodies, invalid Content-Length and strict or repeated query keys. `service.ts` reloads current authorization and lease eligibility before acceptance. The read operations reload the current user and exclude demo leases and tenants.
- `storage.ts` stages into exclusive private temporary files, enforces the byte ceiling while reading, hashes bytes and cancels stalled reads on abort. Root validation requires a canonical directory owned by the app user with no group or other access. Storage keys have a fixed random namespace shape. Reads reject path traversal, directory symlinks and nonregular final files, use O_NOFOLLOW and bounded reads on the opened descriptor, then compare length and SHA-256. A pathname substitution cannot bypass the byte/hash comparison. These checks assume the app-owned private root is not controlled by an adversary with the app's operating-system identity.
- `service.ts:149` enters source gate `73422193` before the nonblocking publication gate `73422195`. `storage.ts:215` counts actual retained regular files, including unreferenced final and partial files, before copying. Retention uses an exclusive partial destination, fsync, rename in the same namespace, and directory/root fsync before metadata publication. `service.ts:173` creates Attachment, DepositEvidence and the acceptance audit in one database transaction. A failed metadata transaction can retain an orphan; it does not turn that orphan into accepted evidence. Only the OS staging input is cleaned automatically.
- `lockAndVerifyDepositEvidence` locks evidence and attachment metadata, validates same-lease ownership and rereads retained bytes through the hash/length verifier. It contains no metadata-only fallback. This proves the verifier's implementation, not that every final deposit posting path calls it; that remains part of the ledger integration review.
- Downloads return verified bytes with attachment disposition, UTF-8 filename encoding, no-store and nosniff. The public DTO omits private filesystem paths and storage keys.
- `formats.ts` permits only the fixed local/internal validator origins and port, requires the exact configured secret shape, rejects redirects, applies a ten-second deadline, bounds JSON responses to 1024 bytes, parses an exact result schema and checks both returned MIME and byte count. Failure cannot accept evidence.
- Validator `server.mjs` authenticates the single raw token header before reading a body, admits at most two operations without a queue, enforces the 5 MiB streaming limit, and covers reading/parsing with an eight-second abort signal. Capacity is released after parser settlement and temporary cleanup. `process.mjs` bounds worker output, starts a detached process group, kills that group on abort and waits for process close before resolving failure. The worker does not receive the token or retained filesystem credentials.
- `validate.mjs` performs actual Sharp raw decoding for bounded single-frame PNG/JPEG images. PDF acceptance requires qpdf syntax success, rejection of encryption and bounded JSON-v2 graph traversal rejecting the contract's restricted action/file names. Envelope checks alone are not treated as structural PDF validation.
- The minimal Dockerfile and Compose overlay specify a non-root validator, read-only root, internal network, private disposable 32 MiB tmpfs, 512 MiB memory/swap limits, one CPU, 64 PIDs, dropped capabilities and no-new-privileges. They mount no database, attachment volume or Docker socket. The Node worker heap flag does not establish a native RSS limit; actual container cgroup configuration must establish that limit.

## Verification status and remaining acceptance gates

This reviewer performed source inspection only and ran no database, native parser, container, browser or privileged operation. Main reported 28/28 native focused validator tests passing after correcting a test fixture that omitted the HTTP Host header, and reported a successful real Docker image build. Those are coordinator-reported results, not independent reruns here. The Host correction preserves the intended authentication test by allowing the request to reach its handler instead of receiving Node's pre-handler HTTP 400.

The app's retained logs report 23 focused tests plus scoped lint/type checks passing. Its six authored PostgreSQL tests require the real isolated validator and were not established as executed at the time of this review. Their genuine-session upload test uses real database authentication with only the Next cookie transport replaced. Their other tests exercise service admission, actual lock exclusion, quota competition and retained-byte verification. This is useful coverage, but authored tests are not passing evidence.

The following gates remain open until Main records actual results:

1. Execute the six PostgreSQL evidence tests with the intended isolated database role and the real validator, including same-actor exclusion and two actors competing for the last retained capacity.
2. Exercise the built Linux image with genuine valid and malformed PDF/JPEG/PNG files, encrypted and active-content PDFs, truncated/oversized inputs, and timeout or parser-failure cleanup. Record actual qpdf/Sharp versions and cgroup, network and mount configuration. A successful image build does not prove PDF CLI/JSON behavior.
3. Prove backup session-lock exclusion against upload publication in PostgreSQL and retain end-to-end backup/restore file verification. The upload's correct publication key alone does not prove the separate backup implementation.
4. Inject metadata/audit transaction failure after durable retention. Verify rollback leaves no accepted metadata and that the orphan remains counted and inventoried. Verify destination partial retention after a publication failure.
5. Verify disabled/demoted users, expired sessions and wrong Origin through the actual routes, and run genuine retained upload/list/download browser UAT. Confirm every integrated financial posting invokes the retained-byte verifier.

No source changes are requested by this review. These open gates prevent a completed Stage 3E acceptance claim until their actual results are reviewed. The agreed project boundary remains completion through Stage 3E and Phase 4, then stop without Go-Live.
